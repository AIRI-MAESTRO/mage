## 1. Что произошло

Три прогона в ad-hoc режиме, модель `deepseek/deepseek-v4-flash`, deep mode:

| Прогон | Запрос | Результат |
|---|---|---|
| 096 | «какая погода там где какой у меня ай пи страны и что мне стоит надеть?» | **Фактический провал** (извинение), но `status: success` |
| 731 | «какой у меня ip» | OK (185.189.46.80), 144s, 52k токенов |
| 773 | «а какой стране принадлежит мой айпи?» | OK (Швеция), 237s, 46k токенов |

Составной запрос требует **трёх последовательных внешних вызовов** (IP → геолокация по IP → погода по локации) + рекомендацию. Простые запросы — по одному вызову, поэтому они прошли.

### Хронология сбоя (прогон 096, по session-логу)

1. **DomainAnalyzer**: `complexity: simple`, `suggested_step_count: 2` — составной запрос классифицирован как простой.
2. **StepPlanner**: подчинился лимиту в 2 шага и **запихнул три HTTP-вызова в один tool-шаг**: rough_aim = «Call http_request to get IP and country from ip-api.com, *then* call a weather API (wttr.in)…». Один `http_request` физически делает один запрос.
3. **StepDescriber**: конкретный URL на этапе генерации неизвестен (зависит от IP, которого ещё нет) → дескрайбер скопировал паттерн из worked example промпта (`{"query": "$outer_context"}` для web_search) и выдал `tool_input_mapping={'url': '$outer_context', 'method': 'GET'}`.
4. **Валидация**: ничего не проверило, что `url` похож на URL. Verifier/Critic выключены по умолчанию.
5. **Исполнение (CARE)**: `$outer_context` = текст вопроса → `GET https://какая погода…` → `Invalid IDNA hostname`. Ошибка вернулась **строкой с `success: true`** → retry_max=3 не сработал, replan выключен (`replan.enabled: false`), ledger записал `status: success`.
6. **Synthesiser**: извинился и **предложил пользователю переформулировать запрос** — переложил вину на пользователя.

В прогонах 731/773 дескрайбер захардкодил конкретные URL (ipify, ip-api) — потому и сработало.

### Сопутствующие находки из логов

- **Полный перезапуск пайплайна при сбое одной стадии.** В прогонах 731 и 773: «Generation attempt 1/3 failed (validation errors for CARLStepSchema… / Failed to parse LLM JSON output…); retrying» → все 7 стадий (domain → … → describe) выполняются заново. Отсюда 144–237s и 44k входных токенов на вопрос «какой у меня ip».
- **JSON-хрупкость на deepseek-v4-flash**: оба ретрая вызваны невалидным JSON от дескрайбера. `use_schema_constrained_output` существует, но выключен.
- **Учёт токенов сломан в реестре**: TUI показывает «in 44013 / out 8029», а в replay/ledger — нули и `tokens_in: null`, `cost_usd: null`.
- **Утечка памяти в имя цепочки**: `name: "General — ## What I remember about you (long-term memory)\n- role: ML r"` — дамп долговременной памяти попал в название.
- **Память не работает как память**: в прогоне 096 `hits_count: 4`, но `digest: ""`; прогоны 731/773 — `cold_start: true`, хотя сессия та же; IP в прогоне 773 пришёл из текста диалога, а не из памяти.
- **Память vs реальность**: rough_aim шага 2 захардкодил «user in Russia», а геолокация дала Швецию (VPN) — план опирался на память для live-данных.
- **`web_search` был доступен** и решал погодную часть одним вызовом, планировщик его проигнорировал.

## 2. Корневые причины

- **R1. Жёсткая связка step_count → план.** `prompts.yaml:1102` («Number of steps should match the suggested_step_count») + `prompts.yaml:~305` («simple = 2-3 шага»). Аналайзер считает шаги по «смысловым блокам», а не по числу атомарных внешних вызовов.
- **R2. Нет правила «один tool-шаг = один вызов инструмента»** — ни в промпте планировщика, ни в схеме, ни в валидации.
- **R3. Дескрайбер не знает сигнатур инструментов.** В `step_describer.py` нет передачи input-схем тулов; worked example `{"query": "$outer_context"}` (`prompts.yaml:1060`) — единственный образец, и он опасен для `url`-полей.
- **R4. Нет шаблонирования URL из выходов шагов.** Для «гео по IP из шага 1» нужен `url: "http://ip-api.com/json/$history[1]"` — таких примеров в промптах нет, P-6 ($history[N]) внедрён только как «ссылайся по номеру».
- **R5. Нет детерминированной валидации цепочки.** `chain_repair.py` / `validate_carl_json` не проверяют: url ~ ^https?:// или содержит $-ссылку; обязательные аргументы тула заполнены; плейсхолдер уместен по типу поля.
- **R6. Ошибки тулов маскируются (CARE-сторона).** Ошибка — строка с `success=true` → нет retry, нет replan, ledger пишет success. «Error as data» без флага.
- **R7. Replan фактически мёртв**: `enable_replan_generation=False` (schemas.py:428), дефолтная политика требует checkpoint-шагов, которых никто не ставит.
- **R8. Все quality-гейты выключены в care-профиле**: `enable_step_critique=False`, `enable_chain_verification=False`, `enable_self_refine=False` (schemas.py:452–465), в `configs/care_default.toml` не включены.
- **R9. Ретрай генерации — всем пайплайном**, а не упавшей стадией.
- **R10. Наблюдаемость**: токены/стоимость не доезжают до ledger/replay; `success` в ledger не отражает фактический исход.
